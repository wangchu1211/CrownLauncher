# Crown 构建工作台方案

文档类型：Design / Roadmap

状态：方向已确认，待实施；本轮只完善 Launcher UI，不接入构建能力

日期：2026-10-12

## 目标与产品位置

构建工作台让用户在不深究构建代码的情况下，仍能检查配置、理解 AI 的操作、启动构建并
验收结果。它是 CrownLauncher 的后续页面，独立于 Editor：即使 Editor 尚未构建或无法
启动，工作台也应可用。现有 Projects、Samples 与项目管理流程继续保留。

用户从 UI 操作，AI 和自动化继续使用 CLI。两者复用同一个 CBT 执行逻辑和任务记录，
用户也能在 UI 中看到 AI 发起的构建，不要求 AI 模拟点击按钮。UI 不再维护另一套
模块规则、目标列表、依赖图或功能默认值；这些信息应从 CBT 查询。

## 用户需要看懂的五件事

| 问题 | 界面应呈现的内容 |
| --- | --- |
| 正在构建什么？ | 工作区、分支、提交、未提交修改；目标（如 Editor、Player、Profiler）、Debug / Development / Shipping，以及实际启用的 Features 和作用。 |
| 为什么需要构建？ | 变化的模块、可复用的编译结果、缓存失效原因、需要准备的依赖。无变化时也应解释 no-op，而非只显示瞬间成功。 |
| 现在进行到哪里？ | 准备依赖、生成代码、编译、链接、部署各阶段，真实任务数量、耗时、错误摘要、排队与取消状态。详细日志是可展开的第二层。 |
| 得到了什么？ | 产物路径、对应源码版本、配置、Features、产物清单；按实际产物提供启动 Editor、打开 LookDev 或查看打包结果等操作。 |
| 验证到什么程度？ | 分开展示构建结果、实际运行的测试及结果、跳过和未验证项，以及人工体验待确认的内容。编译通过不等于功能符合预期。 |

显示无法准确量化的阶段时，使用阶段名称与实际计数，不伪造整体百分比或剩余时间。
错误摘要保留原始诊断入口，不能用一句 AI 总结替代编译器或测试结果。

## 执行与数据边界

工作台沿用 [Electron 架构](architecture/electron-launcher.md)：Renderer 通过类型化
preload API 发起受约束的请求，Main 校验工作区、参数与允许的操作，再调用 CBT。
Renderer 不获得任意 shell、任意进程控制或任意目录删除能力。

实施时先核对 CBT 已有的 JSON 查询、graph / explain、action 信息、测试目录和产物
manifest，优先复用。以下是接入需要确认或补齐的合同，不代表现在已经存在完整接口：

- **能力查询**：版本化 schema，列出当前工作区真正支持的目标、配置、Features 和约束。
- **结构化事件**：稳定的任务 ID、阶段、计数、诊断、退出状态和取消结果。人类可读日志
  用于排查，不作为唯一状态解析来源。
- **持久任务记录**：UI 与 CLI 都写入同一合同，记录发起方式、工作区、源码身份、请求
  配置与实际配置、时间、日志、结果、产物及验证范围。重新打开 Launcher 后仍可查询。
- **产物关联**：仅将本次实际产物与任务关联；构建失败后不得把旧产物冒充本次成功结果。
  未提交修改必须明确标记，不能只用分支或 commit 声称可复现。

CBT 仍负责执行、缓存、锁和依赖准备。工作台展示等待锁、排队、运行、取消、失败、
中断和成功等真实状态，不引入第二个构建调度器。取消只针对任务所属进程，不能结束
其他 Editor 或其他工作区构建。Launcher 关闭时，要明确提示运行任务如何处理；重启后
能区分仍在运行与异常中断的任务，不丢失记录或自动重试。

当 CBT 自身无法启动或工具链缺失时，先显示 bootstrap / 环境诊断，不能让工作台跟随
Editor 一起失效。缓存清理如果后续加入，必须预览准确路径、预计影响和受保护目录，
再由用户确认，不因构建失败自动清空缓存。

## 测试与验收由用户把控

日常构建不自动执行完整 Standard。测试是独立选择：展示所选范围、预计工作内容和
实际结果；需要完整 Standard 时由用户明确启动。此方案不恢复之前暂停或关闭的 CBT
goal，也不把未执行的验证显示为通过。

建议每条任务分别记录：构建状态、自动化验证范围、未验证项、人工验收状态。人工体验
确认由用户给出，AI 不应替用户确认。历史结果要显示其对应源码与配置，避免用户把旧
版本的一次通过误认为当前版本已验收。

## 分期与验收标准

### 当前：Launcher 外观完善

参考用户提供的 Codex 桌面界面，使用暖黑底色、窄图标栏、项目侧栏、细分隔线和克制
圆角。提升项目列表、详情、Samples、设置和弹窗的一致性，保留现有项目管理能力。
不放置无法使用的 Build 入口，不宣称本轮已实现构建工作台。

### 第一版：跑通日常构建闭环

集中实现工作区选择、真实配置查询、构建并运行、实时状态、日志与历史结果。验收至少
覆盖：UI 发起与 CLI 发起的任务均可见；正常成功、编译失败、等待锁、取消及中断均能
正确记录；产物来源可追溯；关闭后重新打开仍能查看历史；构建成功但未测试时明确显示
“未测试”；启动操作指向对应产物而非不明来源的旧 Editor。

### 后续：扩展到其他构建入口

在第一版可靠后，逐步接入打包、显式测试、依赖准备与必要的缓存管理。具体入口由 CBT
能力查询驱动，不先在 UI 中硬编码一张“大而全”的菜单。

云构建、分布式调度、远程执行及复杂依赖图编辑暂不做。性能优化优先解决能显著缩短
等待的大头，不为微小收益增加一套复杂机制。

## 实施前需要确认

任务记录的存放位置、schema 版本与兼容策略；跨工作区任务发现；CLI 与 UI 的事件
订阅方式；Launcher 退出时任务生命周期。这些属于后续接入设计，不能通过解析临时
日志或依赖 GUI 常驻来绕过。

相关文档：[Project Manager MVP](project-manager-mvp.md)。本方案扩展后续路线，不改变
当前 MVP “不从源码构建引擎”的已实现边界。
